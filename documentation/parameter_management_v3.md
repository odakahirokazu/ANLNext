# Version 3: パラメータ管理の検討事項

## レコード出力による編集用バッファの変更

### 現時点の判断

パラメータ設定完了後に表示・JSON出力を行い、その後は編集用バッファを
使わないことが元々の想定である。この運用では問題なしとして、現行実装を維持する。
以下は、出力後に編集を再開する使い方では不具合になり得る箇所として記録する。

### 対象と現在の挙動

- `ModuleParameter_record_map.hh`の`output()`、`to_property_tree()`。
- `ModuleParameter_record_vector.hh`の`output()`、`to_property_tree()`。

これらは、格納済みレコードの各要素を`value_info_`の編集用バッファへ取り出し、
値要素が持つ表示・シリアライズ機能を使う。空でないコンテナを最後まで出力すると、
編集用バッファには最後のレコードの値が残る。
メソッドは`const`だが、`value_info_`が指す値要素の保持値は変更される。
メンバ変数を使う値要素の場合は、そのメンバ変数も書き換わる。

### 不具合になり得る条件

- レコードの設定途中で表示・JSON出力を行うと、設定途中の値が上書きされ、
  その後の`insert_to_container()`で意図しない値が登録される。
- 格納済みレコードがあり、初期値をまだ確定していない段階で出力すると、
  その後の初期値確定時に、最後に出力したレコードの値が初期値として取り込まれ得る。

例えば、格納済みレコードとは異なる値を編集用バッファに設定してから出力し、
続けて`insert_to_container()`を行うと、設定した値ではなく出力した値が使われる。

### 今後の検討

出力後の編集をサポートする際や、値要素の設計を見直す際に再検討する。
`value_info_`が要素の定義情報と編集用の値を兼ね、出力もその保持値を読む構造が論点になる。
独立した出力用の一時オブジェクトや、保持値を書き換えずに値を渡して出力する方法を候補とする。

## Interactive modeの位置づけ

元々はinteractive modeによる対話入力が主流であり、編集用バッファを中心とする
パラメータ管理にはその背景がある。現在はinteractive modeをほとんど使用していないため、
今後の扱いを別途検討する。現時点で廃止や仕様変更を決めるものではない。

検討時には、対話入力に必要な編集状態と、通常のパラメータ設定・参照・出力との
関係を整理する。参照・表示・保存が後続処理の挙動を変えないことを設計上の指針とし、
対話入力の都合で共有してきた状態をどこまで共有する必要があるかを見直す。
